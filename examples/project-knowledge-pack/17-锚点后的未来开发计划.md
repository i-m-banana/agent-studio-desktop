# Agent Studio Desktop：锚点后的未来开发计划

## 路线原则

后续开发以 `1.0.0` 正式锚点为基线，不重写已经稳定的版本、RAG、执行网关和 MCP 主链。每个阶段都必须同时具备：清晰用户价值、数据与安全边界、自动化回归、真实验收步骤、知识包更新。规划能力不能提前写成已完成功能。2026-09-13 起，用户明确将简历已经声明但尚未落地的 Coding、SSH/SFTP 和网站部署验证闭环设为最高产品优先级；会话附件、RAG 第二阶段和 MCP 扩展保留在路线图中，但不再先于这条主线。

## P0：完成 1.0.0 正式版验收

目标不是增加功能，而是把候选版变成可精确恢复的正式锚点。

工作包括：在用户日常 MySQL 上验证 Flyway V10；从前端保存 DeepSeek/Tavily 密钥并重启验证 DPAPI 持久可用；验证环境变量覆盖；验证 v1/v2 默认显示、历史开关、归档、恢复和有引用版本禁止删除；重新运行发布检查和四件套备份；审阅工作区后提交并创建 `1.0.0` 标签。

完成标准：系统诊断的必要项 READY；31 个测试和前端生产构建通过；人工主链通过；备份可用；Git 工作区干净且存在可定位标签。

## P1：会话直接读取附件

这是最直接的产品体验缺口。用户应能像在通用对话产品中一样，把文件附到当前问题，而不必先创建知识库、上传、绑定 Agent、重新发布。

设计分两条：小文件解析后直接进入当前会话上下文；大文件进入 conversation-scoped 临时索引，只能被该会话检索。上传时让用户选择“仅当前会话”或“保存到知识库”。清空会话时清理临时文件和向量，显式转存后才进入长期知识库。

首版格式为 TXT、Markdown、PDF、DOCX。扫描 PDF 和图片 OCR 单独排期，因为当前 DeepSeek 文本模型配置不能等同视觉模型。需要补附件大小/数量限制、恶意文件解析隔离、来源展示、重复文件哈希和清理失败巡检。

验收标准：同一文件仅当前会话可见；另一个会话无法召回；转存知识库后新会话可检索；清空会话后三处临时数据消失；回答仍展示附件名和片段来源。

## P2：RAG 质量第二阶段

目标从“语义向量优于基线”提升到“能判断证据是否足够，并在材料增长后保持排序质量”。

第一步增加章节标题、页码、文档层级和 chunk 邻接关系，改造结构化切块；第二步建立 BM25 与向量混合召回；第三步只对 top-N 候选增加轻量 rerank；第四步增加 evidence judge 或分数间隔规则，专门处理无答案问题；第五步把最终答案是否拒答、引用是否支持结论加入评测。

每项改动都在冻结开发集上做消融，不一次叠加全部策略。核心指标包括 Recall@5、MRR、无答案误召回率、最终拒答准确率、引用支持率、p50/p95 延迟和本机资源占用。只有收益超过复杂度和延迟成本时才进入默认配置。

## P3：文档与索引后台任务化

当前解析、embedding 和重建在同步请求中执行，大文档会占用请求。后续增加 Job/Task 状态，支持上传后立即返回、进度查询、失败重试、取消和应用重启后的安全收口。

任务化先覆盖文档解析、批量 embedding 和知识库重建，不急于引入 Redis 或消息队列；单机版可以使用 MySQL 任务表和有界线程池。只有出现多实例需求时再讨论外部队列。

验收标准：浏览器刷新不丢进度；失败显示具体阶段；重复重试幂等；取消不会留下半套活动索引；旧索引在新索引完整就绪前仍可查询。

## P4：MCP 生产化

当前核心协议闭环已完成，下一步按真实 Server 需求逐项扩展，而不是宣称一次覆盖全部协议。

优先顺序：OAuth 2.1 + PKCE 和安全令牌生命周期；resource templates 与 list_changed 通知；连接健康检查和能力变更提示；可信 Server/工具策略模板；stdio 可执行程序白名单、资源配额与 Windows 沙箱；有数据证明握手成本后再设计长 session 或进程池。

sampling、elicitation 和 roots 会改变 Host 与 Server 的控制关系，必须单独设计用户交互和授权边界。OAuth Token 应复用安全凭据层，但刷新令牌、过期和撤销不能只用当前静态 API Key 接口冒充。

## P5：运行器与审批策略升级

增加客户端断开自动取消、幂等工具标识、重复调用检测、只读工具安全并行和基于运行类型的超时预算。之后再研究持久化检查点和人工恢复，而不是简单重放上一轮外部副作用。

审批从固定 LOW/HIGH 扩展为策略规则：按工具、目标、参数模式、Agent 和可信 Server 决定直接执行、逐次审批或拒绝。单机版可先使用本地策略，不引入身份；若转向团队平台，再增加登录、RBAC、审批人和审计签名。

## P1：Coding 与 SSH 垂直样例

进度（2026-09-18）：Coding 的只读浏览、受审文本补丁和三种固定本地验证任务已经完成自动化与真实主链验收。SSH 只读阶段的页面配置、固定主机指纹、密码安全解析、单远程根 SFTP 浏览/搜索/读取已经通过进程内自动化及真实 Ubuntu 服务器/模型验收。远程既有 UTF-8 文件的摘要绑定精确补丁在修复 OpenSSH SFTP v3 兼容问题后，也完成批准修改、恢复、拒绝和陈旧摘要验收。固定 Git 状态/差异摘要及 Maven/npm 测试构建的受控 SSH Exec 也已完成自动化与真实正向主链验收，并验证非零退出、超时关闭及错误项目标记。任意 Shell、Git 修改、依赖安装、文件新建/删除、Docker/Nginx 与部署仍是计划。

先做 Coding 本地受控工作区：列文件、搜索、读取、生成补丁、用户审批后应用、运行白名单构建/测试。读操作与写操作必须分级，路径始终限制在授权根目录，补丁前后保存摘要和验证结果。

SSH 随后使用隔离的 OpenSSH 测试容器开发：连接配置安全保存；只读命令先行；写入、进程控制和提权命令进入 HIGH/PRIVILEGED；远端目标、命令和工作目录绑定审批。不能把通用 MCP 工具直接宣传成 SSH 能力。

两个垂直能力继续复用 AgentVersion、ToolRegistry、SafeExecutionGateway、ApprovalRequest、RunStep 和 AuditEvent，不新建绕过安全控制的快捷链。

## P7：桌面产品化与可观测性

在主能力稳定后增加安装包、首次启动向导、依赖检测与引导、自动更新策略、日志查看与脱敏导出、磁盘占用管理、知识库/运行保留策略和可恢复卸载。界面增加更清晰的失败阶段、操作撤销和无障碍支持。

可观测性先服务本机排障：结构化日志、request/run 关联 ID、模型与工具延迟、token/额度估算、索引任务耗时和健康趋势。默认不上传遥测；若以后增加匿名遥测，必须显式征得用户同意并说明字段。

## 长期分叉决策

如果产品保持个人桌面定位，就优先离线、低运维、单用户安全存储和本地插件体验，不引入多租户架构。如果真实需求转为团队共享，再单独立项身份、租户隔离、远程数据库、对象存储、队列、多实例租约和合规审计。不能让未验证的“未来可能上云”提前污染当前单机架构。

## 推荐实施顺序

1. P0 正式版验收与 Git 标签；
2. P1 本地 Coding 受控工作区；
3. P1 SSH/SFTP 与个人网站远程运维；
4. P1 Docker/Nginx 部署、健康检查与失败收口；
5. P5 运行与审批策略随副作用能力同步增强；
6. P2 RAG 证据与混合检索；
7. P3 会话附件和后台索引任务；
8. P4 MCP OAuth/通知/沙箱；
9. P7 安装与可观测性。

这个顺序优先把简历声明转化为可演示、可测试、可追溯的真实能力。Coding、SSH 和部署不会一次性宣称完成，而是按“只读浏览—受审补丁—本地验证—远程只读—远程变更—部署验证”的顺序逐段验收。每个阶段结束都应重新生成验证证据，并在知识包中标明“已完成、已自动验证、已真实验证、仍有限制”四种状态。
