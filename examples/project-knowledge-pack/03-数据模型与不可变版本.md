# Agent Studio Desktop：数据模型与不可变版本

## 核心实体

`ModelProfile` 保存模型显示名称、供应商、API 地址、模型名、密钥环境变量名和温度。它不保存密钥明文。

`AgentDefinition` 表示可编辑的 Agent 草稿，包含名称、描述、草稿模型标识、可选草稿知识库标识、系统提示词和最新版本号。状态由版本号推导：尚未发布是 DRAFT，至少发布过一次是 PUBLISHED。

草稿工具绑定保存在 `agent_tool_binding`。发布时把工具名复制到 `agent_version_tool`，所以后来取消草稿工具不会改变旧版本；要改变运行能力必须发布新版本。这与模型配置、系统提示词和知识库快照遵循同一原则。

`agent_run` 记录一次对话运行的会话、AgentVersion、状态、开始/完成时间和错误。`run_step` 按 step_number 记录 MODEL_CALL、TOOL_CALL、TOOL_RESULT，以及工具调用标识、工具名、输入、输出、耗时和状态。当前步骤用于可观测与审计，不等于已经具备崩溃恢复或补偿事务。

`approval_request` 记录高风险调用的 runId、toolCallId、工具名、完整参数 JSON、参数 SHA-256、状态、理由、创建/过期/决定时间。相同 runId 与 toolCallId 只能创建一次。状态从 PENDING 进入 APPROVED、REJECTED 或 EXPIRED；批准后执行前还要以原参数哈希原子转换为 CONSUMED，防止同一次批准被重放或替换参数。

`AgentVersion` 是发布快照。它除了保存关联标识，还复制模型名称、供应商、API 地址、模型名、密钥环境变量名、温度、系统提示词和知识库标识。复制这些字段的目的，是避免后续修改 ModelProfile 或草稿改变历史运行含义。

`Conversation` 在创建时绑定一个 `agentVersionId`。后续使用同一个 conversationId 请求不同版本时，后端返回冲突错误。`Message` 保存 user 和 assistant 消息，并按创建时间恢复上下文。

`KnowledgeBase` 是知识容器。`KnowledgeDocument` 保存文件名、媒体类型、大小、SHA-256、本地路径、处理状态、chunk 数、失败原因和时间。旧向量表 `knowledge_chunk` 保存 384 维 LocalHash；新表 `knowledge_chunk_v2` 保存 1024 维 Qwen 向量，并增加 embeddingModel 和 embeddingVersion。两代索引隔离，不能把不同模型或维度的数据混在一次距离计算中。

## 发布流程

发布 Agent 时，服务通过 `SELECT ... FOR UPDATE` 锁定草稿行，读取当前模型配置，把草稿内容和模型参数复制为新 AgentVersion，再把 latestVersionNumber 加一。发布方法位于 MySQL 事务中，数据库唯一约束保证同一个 Agent 的版本号不能重复。

这种设计解决两个问题。第一，配置可继续编辑，但历史版本稳定；第二，会话能被准确复现，因为它始终知道当时使用的是哪个快照。代价是版本表存在字段冗余，但对可审计和可解释运行来说是有意的反范式设计。

例如管理员后来修改 ModelProfile 的模型地址或温度，旧会话仍从自己绑定的 AgentVersion 读取发布时复制的 baseUrl 和 temperature，而不是回查当前 ModelProfile。因此“旧会话可复现”指运行配置的含义稳定，不代表外部模型供应商本身会永远返回完全相同的文本。

## Flyway 演进

V1 建立模型、Agent 草稿、Agent 版本、会话和消息表。V2 增加知识库和文档元数据表，并在 AgentDefinition、AgentVersion 上增加知识库外键。V3 增加工具绑定、版本工具快照、AgentRun 和 RunStep。V4 增加 ApprovalRequest。应用启动时 Flyway 只迁移 MySQL；pgvector 的 extension、chunk 表和 HNSW 索引由向量初始化器以 `IF NOT EXISTS` 创建，不会在启动时清空数据。

## 版本机制的面试表达

可以把草稿和版本类比为“编辑区与发布制品”。草稿允许变化，发布制品一旦生成就不可修改；新需求通过发布 v2 解决，而不是覆盖 v1。一次会话固定使用一个制品，因此不会出现聊到一半模型、提示词或知识库突然变化的问题。
