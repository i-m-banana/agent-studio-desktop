# Agent Studio Desktop：数据模型与不可变版本

## 核心实体

`ModelProfile` 保存模型显示名称、供应商、API 地址、模型名、凭据名称和温度。它不保存密钥明文。凭据值位于进程环境或 Windows DPAPI 安全存储，独立于业务表。

`AgentDefinition` 表示可编辑的 Agent 草稿，包含名称、描述、草稿模型标识、可选草稿知识库标识、系统提示词和最新版本号。状态由版本号推导：尚未发布是 DRAFT，至少发布过一次是 PUBLISHED。

草稿工具绑定保存在 `agent_tool_binding`。发布时把工具名复制到 `agent_version_tool`，所以后来取消草稿工具不会改变旧版本；要改变运行能力必须发布新版本。这与模型配置、系统提示词和知识库快照遵循同一原则。

MCP 增加 `mcp_server`、`mcp_tool_catalog`、`mcp_resource_catalog`、`mcp_prompt_catalog` 和 `mcp_sync_event`。Server 保存传输配置、环境变量名、协商结果和当前状态；工具目录保存 Schema、风险策略、active 状态与描述指纹；Resource 目录以 URI 哈希形成稳定 publicId，保存媒体类型和大小；Prompt 目录保存参数描述与内容指纹；同步事件保存三类能力数量、工具差异和失败原因。平台工具名包含 Server id 与指纹，因此两个 Server 的同名工具不会冲突，远端描述或 Schema 更新也不会覆盖旧修订。`agent_tool_binding` 和 `agent_version_tool` 仍只引用稳定平台名，沿用原有草稿和发布机制。

`agent_run` 记录一次对话运行的会话、AgentVersion、状态、开始/完成时间和错误。除 CREATED、THINKING、TOOL_RUNNING 等过程状态外，现在还有 CANCEL_REQUESTED、CANCELLED、TIMED_OUT 和 INTERRUPTED。`run_step` 按序记录模型、工具、审批和 RUN_TERMINATION。运行历史接口返回最近摘要，详情接口返回完整步骤；这些记录支持复盘，但仍不能用于断点续跑或补偿事务。

`approval_request` 记录高风险调用的 runId、conversationId、agentVersionId、toolCallId、工具名、能力、风险、目标环境、完整参数 JSON、参数 SHA-256、状态、理由、创建/过期/决定时间。相同 runId 与 toolCallId 只能创建一次。状态从 PENDING 进入 APPROVED、REJECTED、EXPIRED 或 CANCELLED；批准后执行前还要以原参数哈希原子转换为 CONSUMED，防止同一次批准被重放或替换参数。

`audit_event` 记录安全执行网关事件，包含运行、会话、版本、事件类型、工具、能力、风险、状态、参数摘要、说明和时间。它有意不保存原始参数与完整工具输出，避免审计本身扩大秘密和业务数据的暴露面。运行详情会同时查询 RunStep 与 AuditEvent。

`AgentVersion` 是发布快照。它除了保存关联标识，还复制模型名称、供应商、API 地址、模型名、密钥环境变量名、温度、系统提示词和知识库标识。复制这些字段的目的，是避免后续修改 ModelProfile 或草稿改变历史运行含义。

V10 为 AgentVersion 增加 `archived_at`，但归档不修改版本内容。归档版本不能创建新会话，历史 Conversation、AgentRun 和 RunStep 仍然可查。永久删除受到三项约束：必须不是最新版本、必须已经归档、Conversation 与 AgentRun 引用必须为零。这样可以清理误发版本，同时不破坏审计和外键。

`Conversation` 在创建时绑定一个 `agentVersionId`。后续使用同一个 conversationId 请求不同版本时，后端返回冲突错误。`Message` 保存 user 和 assistant 消息，并按创建时间恢复上下文。

`KnowledgeBase` 是知识容器。`KnowledgeDocument` 保存文件名、媒体类型、大小、SHA-256、本地路径、处理状态、chunk 数、失败原因和时间。旧向量表 `knowledge_chunk` 保存 384 维 LocalHash；新表 `knowledge_chunk_v2` 保存 1024 维 Qwen 向量，并增加 embeddingModel 和 embeddingVersion。两代索引隔离，不能把不同模型或维度的数据混在一次距离计算中。

## 发布流程

发布 Agent 时，服务通过 `SELECT ... FOR UPDATE` 锁定草稿行，读取当前模型配置，把草稿内容和模型参数复制为新 AgentVersion，再把 latestVersionNumber 加一。发布方法位于 MySQL 事务中，数据库唯一约束保证同一个 Agent 的版本号不能重复。

这种设计解决两个问题。第一，配置可继续编辑，但历史版本稳定；第二，会话能被准确复现，因为它始终知道当时使用的是哪个快照。代价是版本表存在字段冗余，但对可审计和可解释运行来说是有意的反范式设计。

例如管理员后来修改 ModelProfile 的模型地址或温度，旧会话仍从自己绑定的 AgentVersion 读取发布时复制的 baseUrl 和 temperature，而不是回查当前 ModelProfile。因此“旧会话可复现”指运行配置的含义稳定，不代表外部模型供应商本身会永远返回完全相同的文本。

## Flyway 演进

V1 建立模型、Agent 草稿、Agent 版本、会话和消息表。V2 增加知识库和文档元数据表，并在 AgentDefinition、AgentVersion 上增加知识库外键。V3 增加工具绑定、版本工具快照、AgentRun 和 RunStep。V4 增加 ApprovalRequest，V5 增加 AuditEvent，V6–V7 增加 MCP HTTP、stdio 与管理字段，V8 增加 Resource/Prompt 目录，V9 增加同步历史，V10 增加 AgentVersion 归档生命周期。应用启动时 Flyway 只迁移 MySQL；pgvector 的 extension 和 chunk 表由向量初始化器以 `IF NOT EXISTS` 创建，不会在启动时清空数据。

## 版本机制的面试表达

可以把草稿和版本类比为“编辑区与发布制品”。草稿允许变化，发布制品一旦生成就不可修改；新需求通过发布 v2 解决，而不是覆盖 v1。一次会话固定使用一个制品，因此不会出现聊到一半模型、提示词或知识库突然变化的问题。
