# Agent Studio Desktop：开发过程与提交时间线

## 阶段 0：独立工程基线

第一个提交是 `de8dd90 chore: establish agent studio desktop baseline`。这一阶段建立独立 Git 仓库、Spring Boot 单体、React + TypeScript + Vite 前端、Docker Compose、健康检查、README、架构决策和来源边界记录。

实际环境确认 Maven 使用 Java 21.0.4，Node.js 为 22.13.1。后端测试最初有 2 个，真实启动在 8080，`GET /api/system/status` 返回 UP。前端 TypeScript 和 Vite 构建通过。

## 数据库端口冲突修复

第二个提交是 `a7552f9 fix: avoid local database port conflicts`。MySQL 最初尝试映射 3306，但 Windows 本机已有进程占用；调整为 13306 后仍被占用。最终默认宿主机端口改为 23306，pgvector 使用 15432，并允许通过 `.env` 覆盖。容器内端口没有改变。

## 阶段 1：Agent Builder 和流式对话

第三个提交是 `818c172 feat: add agent builder and streaming chat`。这一阶段新增 Flyway V1、ModelProfile、AgentDefinition、AgentVersion、Conversation 和 Message；实现模型配置、Agent 草稿、发布、版本列表和 OpenAI 兼容 SSE 对话；前端增加模型配置、Agent Builder 和对话测试台。

版本隔离测试验证：修改模型配置和草稿后，v1 快照不变，v2 使用新配置。SSE 集成测试验证 `run → delta → done`。用户随后配置 DeepSeek，发布测试 Agent，并真实收到中文流式回答。

## 阶段 2：知识库和 RAG

第四个提交是 `199572c feat: add local knowledge retrieval workflow`。新增 Flyway V2、知识库与文档元数据、Tika 解析、文本切分、本地 384 维词法向量、pgvector 表和 HNSW 索引、知识库绑定、sources SSE 事件，以及前端知识库页面和来源展示。

真实验收创建了“科研助手验收库”和“科研知识助手”。示例 Markdown 上传后状态 READY，对话返回来源文件、chunk 0 和相似度。删除测试确认 MySQL 元数据、本地文件和向量检索结果同时消失，重新上传后恢复。

## 开发方法

整个过程遵循“先小闭环、后扩展”的顺序。每阶段先确定不能做什么，再实现一条主链；构建或真实运行遇到问题时先保存证据、定位根因、做最小修复，然后重新测试。项目在基础版本、会话和 RAG 稳定并完成收益评测后，才进入工具运行时，仍暂缓 SSH 和 Coding，避免一次引入过大的状态空间。

## 第六阶段：低风险工具与显式 ReAct

2026-09-04 开始实现工具运行时第一阶段。新增 Flyway V3、ToolRegistry、current_time、Agent 草稿/版本工具绑定、OpenAI 兼容非流式 tool_calls、AgentRun 和 RunStep。执行循环由平台显式控制：模型提出调用，平台检查版本授权并执行，再把 Observation 交给模型续答。

安全限制与功能一起落地：默认最大 4 轮、单轮最多 4 次调用、单工具超时；工具失败写入步骤并反馈模型，越权调用和达到上限直接停止。前端可勾选工具并显示模型调用、工具参数、结果、耗时和状态。真实 MySQL 已从 Flyway V2 升级到 V3，自动化测试扩展到 12 个。

2026-09-05 的首次人工配置先暴露出前端缺少编辑已有 Agent 的入口，于是补齐编辑草稿、表单回填、取消编辑和精确重名提示。随后用户创建全新的“查时间”仍失败，截图证明此前的同名归因错误。最终定位为“不使用知识库”的空字符串被写入可选外键；前端改传 null，后端统一归一化空值，并补充回归测试。

用户随后用 DeepSeek 实测“查时间”Agent。MySQL 中的运行记录证明模型真实返回 tool call，平台依次写入 TOOL_CALL、current_time 的 TOOL_RESULT，再发起最终 MODEL_CALL；上海、北京和伦敦时区都得到结果，同一时区的后续问题还体现了模型按上下文判断无需重复调用。因此真实供应商的工具协议兼容性不再只依赖 mock。

## 第七阶段：参数绑定的高风险审批

2026-09-05 在低风险链路验证后增加 Flyway V4、ApprovalRequest 和 HIGH/WRITE 的 write_workspace_note。该工具只能在 `data/tool-workspace` 下新建 `.md` 或 `.txt`，文件名白名单、路径规范化、内容长度和禁止覆盖共同限制写入范围。

当模型请求 HIGH 工具时，运行转为 WAITING_APPROVAL，前端显示工具名、完整参数、SHA-256 摘要和过期时间。用户通过独立接口批准或拒绝；批准后必须用原参数哈希原子消费一次，拒绝或 90 秒超时则不执行并把结果作为 Observation 交还模型。自动化测试增至 15 个，覆盖参数绑定、一次性消费、受控目录写入、路径穿越拒绝和端到端拒绝不执行。

用户人工验证了两条高风险链路：`approval-reject-test.md` 被拒绝后没有创建，`approval-accept-test.md` 批准后成功写入受控目录。这说明真实 DeepSeek tool call、浏览器审批、后端一次性消费和文件副作用已经串成完整闭环。

## 第八阶段：运行取消、总时限与历史详情

2026-09-05 增加 RunControlService。每个执行线程按 runId 注册，独立调度器在默认 120 秒截止时发出 TIMED_OUT；用户可从对话页提交取消，使状态先进入 CANCEL_REQUESTED，随后由执行线程收口为 CANCELLED。终止信号在模型流式回调、ReAct 每轮、审批等待和工具异常边界重复检查，避免取消被普通工具失败处理吞掉。

前端新增“停止运行”和“运行记录”页面，后端新增最近运行列表、详情和取消接口。RUN_TERMINATION 保存最终原因；应用启动时把旧进程遗留的运行关闭为 INTERRUPTED、审批关闭为 EXPIRED。这里刻意没有宣称断点续跑，因为模型请求和外部副作用还没有可安全重放的检查点。自动化测试增至 17 个，覆盖阻塞模型调用的主动取消、总超时、terminated SSE、历史摘要和终止步骤。

提交前复核还发现一个并发窗口：取消请求可能恰好发生在最后一次信号检查之后、COMPLETED 写入之前。修复方式不是再加一次普通检查，而是让最终状态更新携带数据库前置条件；COMPLETED/FAILED 不能覆盖 CANCEL_REQUESTED，只有取消/超时/中断收口可以从非终态转为对应终态。这样把正确性落到原子状态迁移上，而不是依赖线程时序。

用户随后在真实 DeepSeek、MySQL 和浏览器环境验收两条终止路径：运行 `86918b87` 点击停止后变为 CANCELLED，保留 4 个步骤和“用户主动取消运行”的原因；运行 `f72e72ab` 保持运行至默认 120 秒截止后变为 TIMED_OUT，保留 7 个步骤和明确超时原因。由此，运行治理不再只有 mock 自动化证据。

## 第九阶段：统一安全执行网关与结构化审计

2026-09-05 在接入 SSH 前先补齐横向安全层。此前 ChatService 同时负责 ReAct、风险判断、审批和工具执行，继续增加适配器会让安全规则散落。重构后所有工具交给 SafeExecutionGateway，固定经过 Schema 校验、风险判断、参数绑定审批、取消检查、限时执行和审计，ChatService 只保留编排与 RunStep。

## 第九阶段：MCP 动态工具核心闭环

2026-09-05 用户确认 MCP 是核心模块后，新增 Flyway V6、MCP Server 配置、Streamable HTTP 客户端、工具目录和前端连接页。实现时没有把 MCP 调用直接塞进 ChatService，而是让动态工具加入原 ToolRegistry，从而复用已经验证的版本绑定、Schema 校验、审批、超时、取消、RunStep 和 AuditEvent。

协议实现依据 MCP 2025-06-18：初始化必须是首个交互，随后发送 initialized；tools/list 支持 nextCursor；POST 响应同时接受 JSON 和 SSE；有状态 Server 返回的 Mcp-Session-Id 与协商后的 MCP-Protocol-Version 会用于后续请求。工具调用结束后尽力 DELETE session，服务不支持时允许 405。

开发中专门处理了两个平台问题。第一，远端工具名不能直接作为平台主键，因此增加 Server 命名空间与描述指纹；第二，远端自报只读不能等同可信策略，因此所有 MCP 工具首版默认 HIGH。随项目增加了不依赖 npm 包的 Node fixture Server，使手工验收不受第三方服务和凭据影响。自动化从 20 个增至 23 个，前端构建通过；真实 MySQL 和 DeepSeek 全链路等待用户重启后端后验证。

Flyway V5 新增 AuditEvent，并给 ApprovalRequest 补齐 conversationId、agentVersionId、能力、风险和目标环境。审计记录校验、等待审批、审批结果、执行开始、完成、跳过、失败或终止，但只保存参数 SHA-256 和输出长度/耗时等摘要。前端运行详情同步展示安全审计。第一轮构建暴露出 ReAct 私有方法没有传 conversationId，导致审计上下文无法编译；补齐方法参数后全量测试通过。自动化测试增至 20 个，并增加缺字段、额外字段和错误类型三类通用 Schema 拒绝测试。

## 阶段 3：评测驱动的语义向量升级

评测提交 `98b3351` 建立 30 道冻结题集和 LocalHash 基线，`15ec1cd` 完成 Qwen embedding-only 候选对照。数据证明 Qwen 对低词面重合改写有明显收益，因此生产增加 EmbeddingGateway、1024 维版本化索引和显式重建入口。

实现期间又做了 query instruction 消融：在知识包扩充前的同一语料上，统一中文前缀令 MRR 从 0.8160 降到 0.6917，最终默认关闭。知识包随后补入升级过程与故障复盘，LocalHash 与 Qwen 又在新语料上同时重跑。这个过程体现了项目用指标决定配置，并在语料变化后重建可比基线；最终数值不反写到参与评测的 00–10 正文，以免形成指标与语料相互改写的循环。
