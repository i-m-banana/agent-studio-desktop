## 为什么自动化和真实验收都要有

自动化测试适合保证版本隔离、协议结构和算法不回归，但无法证明 Docker 端口、真实数据库方言、环境变量继承和外部模型兼容。真实验收能覆盖这些问题，却不适合每次提交都执行。因此项目把两类证据分开记录。

MCP stdio 阶段全量后端为 24 个测试、0 失败、0 错误，H2 从 V1 迁移到 V7。新增协议测试不是把进程 API mock 掉，而是用 Java 测试真实启动项目附带的 Node stdio Server，完成 initialize、initialized、tools/list、第二次独立进程 tools/call 和退出回收。管理集成测试还覆盖首次同步 added=1、再次同步 unchanged=1、单工具停用、Server 停用和未引用 Server 删除。前端再次通过 TypeScript 与 Vite 生产构建。

MCP 收口阶段保持 24 个测试，但扩大了现有协议与集成用例的覆盖面。HTTP 进程内 fixture 和真实 Node stdio fixture 都声明 tools/resources/prompts，并在独立短 session 中验证分页目录解析、resources/read、prompts/get 和 tools/call。服务集成测试验证 Resource/Prompt 目录落库、必填参数后的调用委托、两次 READY 同步历史和无秘密配置导出。H2 从空库顺序执行 V1–V9，前端再次通过 TypeScript 与 Vite 生产构建。

人工验收 stdio 时，不需要先运行常驻服务：页面选择本机 stdio，程序填 node，参数填 fixture 的绝对路径，保存同步后应看到“查询本机项目状态”。绑定并发布 Agent 后询问 MCP 模块状态，审批目标应显示 `@本机进程`；批准后结果包含“本机 stdio MCP 调用正常”。还应测试停用后工具退出 Agent Builder，以及已引用 Server 的删除请求被明确阻止。
