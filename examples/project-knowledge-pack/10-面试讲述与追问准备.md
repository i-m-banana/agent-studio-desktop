# Agent Studio Desktop：面试讲述与追问准备

## 90 秒项目介绍

我主导做了一个单机优先的智能体搭建工具 Agent Studio Desktop，目标是让用户不改 Java 代码，就能配置 OpenAI 兼容模型、提示词和知识库，发布固定版本的 Agent，并在网页上做流式问答和查看引用来源。后端采用 Java 21 和 Spring Boot 模块化单体，前端是 React + TypeScript，MySQL 保存业务配置，PostgreSQL + pgvector 保存向量，本地文件系统保存原始文档。

我没有直接扩展旧平台，而是先收敛复杂度：放弃多模块 DDD 和动态 Bean，使用可编辑 AgentDefinition 加不可变 AgentVersion，保证历史会话不受后续配置修改影响。开发上先跑通模型配置、发布和 SSE，再加入 Tika 解析、重叠切块、向量检索和 sources 事件。真实环境中解决了 Windows 数据库端口冲突、双数据源自动装配连错库等问题，并用 DeepSeek、MySQL 和 pgvector 完成端到端验收。

当前 RAG 使用本地 384 维词法哈希作为零外部 embedding 依赖的基线，完整流程可用但语义召回有限。下一步会抽象语义 embedding 和索引版本，再做混合检索与离线评测；工具调用和审批则通过显式 ReAct 与统一安全网关逐步增加。

## STAR 故事：双数据源问题

情境：加入 pgvector 后，应用同时有 MySQL 和 PostgreSQL 两个数据源。任务：让 Flyway 只迁移 MySQL，业务 CRUD 使用 MySQL，向量读写只使用 PostgreSQL。

行动：我根据异常中的 `relation does not exist` 和连接池日志定位到自动装配选错连接，而不是表迁移缺失。随后显式定义 primary MySQL DataSource、JdbcTemplate 和 NamedParameterJdbcTemplate，并给四个业务 Repository 加 Qualifier；向量 Repository 固定使用 vectorJdbcTemplate。

结果：真实启动时 Flyway 正确连接 MySQL 8.4，VectorPool 单独连接 PostgreSQL，知识库创建、模型查询、向量写入和检索全部恢复。这个问题让我意识到多数据源不能只标一个 DataSource，还要检查上层 JDBC 模板和每个仓储的注入点。

## 高频追问

问：为什么 AgentVersion 要复制模型字段？答：为了形成发布快照。只存 modelProfileId 会导致模型配置更新后历史版本含义改变。字段冗余换来可复现和可解释。

问：为什么不用 Spring AI？答：当前只需要一个可控的 OpenAI 兼容流式入口，直接 HttpClient 更轻，异常和 SSE 解析路径透明。未来供应商增多时可在 StreamingModelGateway 后增加适配器。

问：为什么 SSE 不用 WebSocket？答：当前是服务端单向推送文本和状态事件，SSE 基于 HTTP、复杂度更低。需要双向实时控制时再考虑 WebSocket。

问：RAG 为什么分三种存储？答：MySQL 管业务关系，本地文件保原件，pgvector 管可重建的检索索引。职责清晰，但跨存储一致性需要后续补偿机制。

问：词法哈希算 embedding 吗？答：它产生固定维度、可做向量距离的数值表示，但不是训练得到的语义 embedding。它是零依赖检索基线，不能夸大语义能力。

问：最有价值的工程决策是什么？答：先用不可变版本和清晰数据边界稳定运行语义，再扩展 RAG；同时把“已实现”和“规划中”写入验证文档，避免演示能力与真实能力不一致。
