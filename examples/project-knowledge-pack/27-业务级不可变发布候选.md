# 业务级不可变发布候选

## 为什么没有把每个技术步骤都做成工具

工具边界按业务意图、授权边界和失败语义划分，而不是按实现步骤划分。Maven 测试、打包、确定 jar、计算摘要、上传和远程校验只服务于“准备发布候选”这一项业务，因此它们是同一工具内的受控步骤。LLM 只能决定是否请求该业务动作，不能接管技术参数。

## 固定链路

`固定本地源码 → Maven 测试 → Maven 打包 → target/app.jar → SHA-256 → 平台 releaseId → 全新远程候选目录 → SFTP 独占上传 → 远程摘要校验`

本地根目录已有的 `app.jar` 不参与选择；工具不会搜索“最新 jar”。本地 `docker-compose.yml` 上传后标准化为候选目录中的 `compose.yml`。

## 与生产发布的区别

候选准备只回答“这一组固定文件是否由当前可信源码构建、完整上传并可按摘要复核”。它不会构建镜像、替换生产文件、读取 `.env`、重启容器或切换流量。真正部署仍应是后续独立的高风险业务工具，并绑定候选 releaseId、发布前备份、健康检查和失败回滚。

## 审计结果

结果包括 releaseId、本地固定制品相对路径、远程候选目录、成功状态、退出码、耗时、制品大小与 SHA-256、manifest SHA-256、有限输出以及是否截断，并明确返回 `productionModified=false` 和 `imageBuilt=false`。
