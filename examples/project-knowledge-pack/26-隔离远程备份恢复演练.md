# Agent Studio Desktop：隔离远程备份恢复演练

## 为什么不直接恢复生产

远程备份已证明能够创建和校验，但直接覆盖生产数据库或 uploads 会把演练变成真实数据变更。系统先增加更窄的材料化演练：验证备份可读取、摘要一致、压缩包可展开、数据库和固定部署文件可复制，同时保持生产目录和运行容器不变。

## 安全模型

`verify_remote_deployment_backup_restore` 是无模型参数的 `SSH/WRITE/HIGH` 工具，继续经过 AgentVersion、ToolRegistry、SafeExecutionGateway、参数绑定的一次性 ApprovalRequest、RunStep 和 AuditEvent。它只选择固定备份根中最新的合格目录，并且只在固定 `restore-drills` 子目录创建全新随机目录。模型不能指定备份 ID、路径、命令、参数、环境变量、数据库或恢复目标。

## 演练内容

执行前校验备份目录、固定文件、`FAILED` 标记、`SHA256SUMS`、manifest 摘要、目标字段和 gzip 完整性，并按展开大小加安全余量检查磁盘空间。随后在隔离目录复制 database.sql、app.jar、Dockerfile、Compose、Nginx 配置和受保护 `.env`，展开 uploads，并比较固定文件；展开后的 uploads 不允许符号链接。演练自身生成 properties 和 SHA-256 回执。

## 能证明与不能证明的事

成功结果能证明备份材料可以在服务器上校验并材料化，且工具没有修改生产目录或导入数据库。它不能证明 SQL 能被目标 MySQL 完整导入，也不能证明应用用这些材料启动后业务一定正常。数据库导入、生产恢复、自动回滚、历史清理和正式发布仍是后续独立阶段。

## 真实验收

运行 `0ff426e4-2fd1-429a-b860-6b0ae62e501c` 从备份 `20260921T143308Z-5b8b3432` 创建 `restore-20260921T145940Z-c5bb4e7f`，材料化 105 个文件，数据库 28,056 字节、uploads 377,940,481 字节，生产未修改、数据库未导入。后续 Compose 配置、四服务状态和真实 `SITE_HEALTH` 均通过。验收中特别排除了一次没有 TOOL_CALL、只有模型健康描述的运行，说明运维证据必须核对 RunStep/AuditEvent，不能只相信自然语言结论。
