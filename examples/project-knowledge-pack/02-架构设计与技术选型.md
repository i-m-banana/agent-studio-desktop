# Agent Studio Desktop：架构设计与技术选型

## 模块化单体

项目选择“Spring Boot 模块化单体 + 独立 React 前端 + 两个数据库容器”。后端只有一个 Maven 工程，通过 `agent`、`model`、`conversation`、`knowledge`、`system` 等 Java package 隔离职责。

这个选择针对的是单机开发工具场景。微服务会引入服务发现、网络调用、分布式事务、部署和日志聚合成本，而当前用户只有一个本地实例，也没有独立扩缩容需求。模块化单体保留清晰边界，又能用一次启动和本地调试完成完整链路。

## 为什么不用动态 Spring Bean

来源平台曾按数据库配置动态注册模型、Advisor、MCP Client 和 ChatClient Bean。动态 Bean 能实现配置驱动，但会把用户配置对象放进全局 Spring 容器，带来同名覆盖、销毁、旧引用、并发更新和运行中会话如何处理等生命周期问题。

新设计只让 Spring 管理稳定基础设施，例如 Model Gateway、Knowledge Retriever、Repository 和 Service。用户配置以普通数据对象存在；发布时形成 AgentVersion 快照，运行时按版本读取。这样仍然支持“不改代码创建新 Agent”，同时版本行为和调试路径更直接。

## 为什么使用 MySQL 和 pgvector 两套存储

MySQL 负责强结构、关系约束和事务明确的业务数据：模型配置、Agent 草稿、版本、会话、消息、知识库和文档元数据。PostgreSQL + pgvector 负责 chunk、JSON metadata 和向量距离计算。本地文件系统保存上传的原始文档，Ollama 负责本地语义向量生成。

三者的职责分别是“业务真相”“检索索引”“原始材料”。这种拆分让业务表不依赖向量扩展，也让向量索引可以独立重建。但跨三种存储的删除没有分布式事务，当前只能显式报错，后续需要补偿任务和孤儿数据巡检。

## Embedding 网关和版本化索引

生产代码通过 `EmbeddingGateway` 隔离 LocalHash 与 Ollama。默认 Qwen 生成 1024 维向量并写入 `knowledge_chunk_v2`，记录模型和索引版本；旧 384 维表继续保留。知识库升级必须由用户显式触发重建，启动应用不会自动改写索引。

当前 Qwen 表采用精确 cosine 排序，不建立 HNSW 向量索引。原因是当前语料规模很小，近似索引没有性能必要，反而可能牺牲召回。表上只对 knowledgeBaseId 和 embeddingVersion 建范围索引。

## 为什么不引入 Redis、MQ 和 MinIO

第一版没有缓存规模、异步吞吐或对象存储集群需求。Redis 和 MQ 会增加 Docker 资源、状态一致性和排障面；上传文件直接放到本地 `data/knowledge` 更符合单机产品。需要恢复的业务状态写 MySQL，向量写 pgvector。

## 前后端通信

普通配置管理使用 HTTP JSON。对话使用 Server-Sent Events，因为当前主要方向是服务端持续向浏览器推送文本增量，SSE 比 WebSocket 更简单，也能自然穿过普通 HTTP 代理。事件包括 `run`、可选 `sources`、多个 `delta`，最后是 `done` 或 `error`。

## 工具运行时边界

工具不是由模型 SDK 自动执行。ToolRegistry 只向模型暴露 AgentVersion 已绑定的描述；模型返回结构化 tool call 后，ChatService 校验绑定关系、解析参数并调用平台工具，再把结果作为 Observation 送回模型。这样模型负责决策，平台掌握真正的执行权。当前有 LOW/READ 的 current_time 和 HIGH/WRITE 的 write_workspace_note，默认最多 4 个工具轮次、每轮 4 次调用，并设置单工具超时。

每次对话都生成 AgentRun。模型调用、工具请求和工具结果形成有序 RunStep，既写入 MySQL，也通过 step SSE 展示到前端。HIGH 工具会额外创建 ApprovalRequest，保存原始参数及 SHA-256、过期时间和一次性状态；批准必须匹配原哈希并原子消费，拒绝或超时不会执行。

RunControlService 在执行线程注册 runId 和截止时间。取消接口先把数据库状态改为 CANCEL_REQUESTED，再发送线程中断；ChatService 在检索、模型、审批、工具和持久化边界检查终止信号，最终写为 CANCELLED 或 TIMED_OUT，并增加 RUN_TERMINATION。应用启动会把上一进程遗留的非终态运行标为 INTERRUPTED、待决审批标为 EXPIRED。它解决的是状态收口，不是断点续跑；当前仍不支持登录身份，也不支持多个后端实例共享数据库。

SafeExecutionGateway 是所有工具的统一执行门。ChatService 只负责 ReAct 编排和 RunStep，不再自行拼装风险判断与执行逻辑；网关依次完成通用 Schema 校验、风险判断、参数绑定审批、取消检查、限时执行和 AuditEvent。这样未来 BUILTIN、MCP、SSH 与 Coding 适配器只提供能力实现，不得绕过同一个安全入口。

MCP 首版采用 `2025-06-18` Streamable HTTP，而不是已被替代的旧 HTTP+SSE。平台作为 Host 中的 Client，先 initialize 协商协议和 tools 能力，发送 initialized，再分页 tools/list；实际调用时发送 tools/call。MCP 工具通过 Server id、远端名称和“名称+标题+描述+Schema”指纹生成稳定平台名，解决跨 Server 重名，并让远端描述或 Schema 变化形成新修订。动态工具仍进入同一个 ToolRegistry，不另建旁路执行器。

外部 Server 的描述和风险提示不能直接信任，因此首版 MCP 工具统一为 EXECUTE/HIGH，必须展示参数与目标 Server 并逐次审批。凭据只保存环境变量名，通过 Authorization Bearer 在后端读取；远程地址必须 HTTPS，本机才允许 HTTP。当前每次调用建立短 MCP session，换取简单清晰的生命周期和故障隔离，后续再按性能证据决定是否池化。

第二版把 `McpTransportClient` 扩展为按 transport 路由，同时加入 stdio。stdio 每次发现或调用都由平台启动一个短生命周期子进程，使用 UTF-8 单行 JSON-RPC 完成 initialize、initialized、tools/list 或 tools/call；stdout 出现普通日志会判为协议错误，stderr 只截取有界尾部用于诊断。调用结束先关闭 stdin 等待，再终止、最后强制结束进程及其后代。短进程会多一次握手，但隔离了跨调用状态、僵尸进程和常驻连接泄漏问题。

stdio 配置不保存一条 shell 字符串，而是“启动程序 + 参数数组”。后端用 ProcessBuilder 直接启动并拒绝 cmd、PowerShell、bash 等解释器，避免把 MCP 配置退化成通用命令执行入口。子进程不会继承后端全部环境，只保留 PATH、系统目录和临时目录等启动基础；需要密钥时只保存“子进程变量名到宿主变量名”的显式引用，运行时读取值。它仍以当前用户权限运行，还没有 OS 沙箱和资源配额，因此只能连接用户明确信任的本机 Server。

MCP 管理语义也区分“停用”和“删除”。停用只让工具退出新调用，不破坏工具目录；若 Server 工具已被 Agent 草稿或历史版本引用，物理删除会被拒绝。同步先把旧工具标为 inactive，再 upsert 当前修订，并返回新增、下线、未变化数量。新工具默认 HIGH；用户可以显式停用、调整超时，或在确认信任后降为 LOW，而平台不会根据远端自报 annotations 自动降权。

第三阶段补全 Resources 与 Prompts。两种传输在 initialize 后根据 capability 独立分页发现三类原语；Resource 以 URI 哈希持久化，读取仍使用短 session，用户可预览或把内容送入既有 KnowledgeService，因此没有复制一条“特殊 MCP 向量化链”。多段文本合并，二进制只允许单段并校验 Base64，总大小仍受 20 MB 限制。Prompt 目录保存名称、描述和参数，`prompts/get` 只在用户主动点击并填参后调用，不让外部 Prompt 悄悄改变 Agent 配置。

同步事件独立保存 READY/FAILED、协议版本、三类目录数量、工具增删和错误，避免 Server 卡片只能显示最后一次状态。配置导出复用同一请求结构，只导出密钥环境变量名或子进程环境映射，不导出秘密值。OAuth 没有用“多填一个 token”冒充：规范要求 HTTP 授权资源元数据、OAuth 2.1、PKCE、资源指示器与安全令牌存储，需单独设计浏览器回调和凭据生命周期。

RunStep 与 AuditEvent 的关注点不同：RunStep 还原模型推理和工具观察序列，AuditEvent 记录安全网关为什么接受、等待、阻止、执行或终止。审计只保存参数 SHA-256 和输出长度、耗时等摘要，避免复制原始参数或完整输出造成额外敏感数据面。

## 端口与部署

前端默认使用 5173，后端使用 8080。为避免 Windows 电脑已有数据库占用默认端口，MySQL 宿主机端口最终定为 23306，容器内仍是 3306；pgvector 宿主机端口是 15432，容器内是 5432。端口可以通过 `.env` 和环境变量覆盖。
