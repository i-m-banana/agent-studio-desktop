# Agent Studio Desktop：正式版发布加固与运维

## 为什么主功能完成后还不能直接叫正式版

截至 2026-09-06，模型、RAG、Agent 版本、工具运行、审批审计和 MCP 核心闭环都已完成并经过人工体验。但“功能能演示”不等于“版本能交付”：进程存活不代表依赖可用，向量相关不代表事实有证据，开发者手工敲多条命令不利于复现，没有备份恢复也无法保护用户已经创建的配置和知识库。因此工程先冻结新功能，以 `1.0.0-rc1` 做发布加固。

## 系统诊断解决什么问题

原来的 `/api/system/status` 只证明 Spring Boot 能响应。新增 `/api/system/readiness` 和前端“07 系统诊断”后，用户能看到六类检查：MySQL 业务数据库、pgvector 向量数据库、Embedding 模型实际推理、对话模型凭据、data 目录写权限和 MCP 连接。

状态分三层：READY 表示可用；DEGRADED 表示可选能力未配置或异常，例如完全不使用 MCP；NOT_READY 表示正式对话或 RAG 的必要依赖失败。诊断只显示 `DEEPSEEK_API_KEY` 这类凭据名，不展示密钥值。早期版本只能继承启动进程环境，因此另一个终端后来设置的值不会生效；第十四阶段增加 Windows DPAPI 安全存储后，用户也可以在前端保存并立即使用。

## RAG 无答案边界

向量检索回答的是“哪段最相似”，不是“哪段足以证明结论”。此前冻结负例的检索误召回率为 100%，说明只靠固定相似度阈值不能解决无答案问题。本阶段没有伪造一个更漂亮的检索指标，而是把检索相关性和答案证据性拆开。

如果绑定知识库的 Agent 完全没有召回满足阈值的片段，且没有工具可补充信息，平台直接回答“知识库中没有足够证据回答该问题”，记录 EVIDENCE_CHECK，不调用大模型。如果存在候选片段，模型会收到严格证据契约：候选不是答案；数字、名称、版本、人员、许可、平台支持和承诺必须被片段直接支持；证据充分时标注来源文件，否则使用同一句拒答。绑定工具的 Agent 即使知识库无结果，也保留调用工具取得证据的机会。

这个方案降低无证据猜测和空召回成本，但不能声称彻底消除幻觉。候选片段场景仍依赖模型遵循指令，未来可用独立 evidence judge、NLI 或 reranker 做第二层判定。检索层负例误召回率和最终答案拒答准确率必须分别评测。

## 自动化补齐了哪些高风险回归

后端测试从 24 个扩展到 30 个。新增用例覆盖：MCP 配置导出只含密钥变量名、Resource 通过统一 KnowledgeService 导入、两个并发会话各自只看到自己的问题和会话标识、两个知识库的 chunk 与文档删除不能串库、空召回确定性拒答且不调用模型、系统诊断接口和版本号。原有测试继续覆盖不可变版本、SSE、工具循环、超时、审批一次性消费、路径穿越、取消、总时限、HTTP/stdio MCP 和安全审计。

知识库隔离测试特意把文件写到 `backend/target/test-data`，避免自动化污染用户的真实 `data`。并发会话测试用同步栅栏让两个模型调用确实重叠，而不是顺序执行两个请求后宣称“并发已测”。MCP Controller 测试补上此前服务层已覆盖、HTTP 入口尚未直接覆盖的配置导出和 Resource 入库边界。

## 一键运行与版本口径

工程根目录 `VERSION`、Maven 和 npm 统一为 `1.0.0-rc1`。`scripts/preflight.ps1` 检查 Maven 实际使用的 Java 21，而不是只看系统 `java` 命令，因为这台开发机的系统 Java 仍为 8、Maven 已明确绑定 Java 21。`scripts/start.ps1` 启动 Compose、后端和前端，把 PID 与日志放进 `.run`；`stop.ps1` 只停止这些记录过的进程，除非显式增加 `-StopDatabases`。

`release-check.ps1` 串联预检、后端全测、前端可复现安装与生产构建、版本一致性和工作区提示。它不能替代真实 DeepSeek、浏览器审批和 MCP 人工验收，所以正式版清单仍保留人工步骤。

## 备份演练中的真实故障

第一次用旧版 Windows PowerShell 运行备份脚本时，内联 Compose 路径和含中文的无 BOM UTF-8 脚本触发了解析差异。修复为先解析固定路径，并让运维脚本保持 ASCII 兼容。

第二次演练中，MySQL 应用账号没有 PROCESS 权限，`mysqldump` 尝试读取 tablespace 后报错；更严重的是 PowerShell 管道使 `$LASTEXITCODE` 被后续写文件命令覆盖，脚本把不完整结果误报为成功。最终增加 `--no-tablespaces`，把数据库输出和原始退出码先保存，只有退出码为零才落盘并生成 manifest。

第三次真实演练成功生成约 88 KB 的 MySQL SQL、364 KB 的 pgvector SQL、26 KB 的 data.zip 和版本清单。恢复脚本没有直接在用户数据上演练，因为那是破坏性操作；已验证不带 `-ConfirmRestore` 会立即拒绝，并限制恢复源必须位于当前项目的 backups 目录。完整恢复应在隔离副本中做灾备演练。

发布检查第一次执行 `npm ci` 时还遇到正在运行的 Vite 锁住 `node_modules/@esbuild/win32-x64/esbuild.exe`，Windows 无法原地删除。最终没有要求用户关闭开发环境，也没有降低为复用旧依赖，而是把 package、配置和 src 复制到随机临时目录，在那里执行干净 `npm ci` 与生产构建；清理前再次校验路径必须位于系统临时目录且名称带固定前缀。这样同时验证可复现安装，并避免碰用户正在运行的 node_modules。

用户第一次实际运行一键启动时，后端已经就绪，但前端报告 30 秒未就绪。读取 `.run/web.err.log` 后确认前一次失败的原地 `npm ci` 已删除部分依赖，`npm run dev` 找不到 vite。执行 `npm install` 后依赖恢复；启动脚本也新增 node_modules 中 Vite 的存在性检查，缺失时自动补装。第一次修复复测又发现 Windows 可能把 `localhost` 解析为 IPv6：Vite 日志显示已启动，但脚本针对 `127.0.0.1` 的 IPv4 健康检查仍然超时。最终把 Vite 明确绑定到 `127.0.0.1`，让监听地址和健康检查保持一致。后台启动从隐藏 PowerShell 改为隐藏 cmd 子进程，避免 Maven 尝试设置无控制台窗口标题时触发 PowerShell HostException；停止脚本也容忍清理瞬间进程自行退出的竞态。最终实测一键启动约 14 秒完成，后端状态为 `UP`、版本为 `1.0.0-rc1`，前端返回 HTTP 200；随后一键停止完整关闭后端和前端。失败分支仍按记录 PID 停止完整进程树，不遗留半启动服务。

## 面试讲法

可以这样概括：主链完成后，我没有继续堆功能，而是按发布风险做了四项收口。第一，用真实依赖诊断区分进程存活和业务就绪；第二，把 RAG 相关性与证据充分性分层，空召回确定性拒答；第三，补并发会话、知识库隔离和 MCP HTTP 边界测试；第四，把启动、发布检查和三类数据备份固化成脚本。备份演练还暴露了 MySQL 权限和 PowerShell 退出码两个问题，说明运维脚本也必须用真实环境验证，不能只做语法检查。

不要把 `1.0.0-rc1` 说成已经发布的正式版。准确口径是：正式版前功能已冻结，自动化和备份演练通过，等待用户完成真实系统诊断、DeepSeek、RAG、审批与 MCP 集中验收后再升为 `1.0.0`。
