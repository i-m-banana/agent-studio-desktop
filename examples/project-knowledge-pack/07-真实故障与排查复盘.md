# Agent Studio Desktop：真实故障与排查复盘

## 故障一：MySQL 端口连续冲突

现象是 Docker 报 `bind: Only one usage of each socket address` 或 `port is already allocated`。3306 被占用后改到 13306仍冲突，最终选择 23306。

根因不是容器内 MySQL 启动失败，而是 Windows 宿主机端口已经被其他进程或容器占用。修复是在 Compose 中只修改宿主机映射，容器仍监听 3306，同时把后端默认连接端口和 `.env.example` 对齐。经验是不能只看容器 Created，要用 `docker compose ps` 确认 healthy 和 PORTS。

## 故障二：系统 Java 与 Maven Java 不一致

系统 `java` 命令指向 Java 8，但 Maven 实际使用 Java 21.0.4。Spring Boot 3.4 项目按 Java 21 编译可以成功，说明判断构建 JDK 应以 `mvn -version` 为准，而不能只看 `java -version`。这类差异在 Windows 多 JDK 环境很常见。

## 故障三：Vite TypeScript 配置失败

前端首次构建因为 `allowImportingTsExtensions` 缺少 `noEmit` 而失败。该选项只允许在不输出 JavaScript或只生成声明时使用。为 Vite 配置工程补充 `noEmit: true` 后，`tsc -b && vite build` 通过。

## 故障四：SSE 中文断言变成问号

SSE 集成测试在 Windows 测试响应字符集下，中文增量断言显示为问号。事件结构和实际流式逻辑没有问题。测试改用与字符集无关的 ASCII 增量文本来验证协议结构，真实 DeepSeek 调用再单独验证中文输出。这个处理把“协议正确性”和“终端显示编码”分开验证。

## 故障五：双数据源自动装配选错数据库

加入 PostgreSQL 向量数据源后，第一次真实启动出现两个问题：Flyway 可能选择 pgvector 数据库；即使 Flyway 已迁移 MySQL，业务 `NamedParameterJdbcTemplate` 仍可能连到 PostgreSQL。表现为向 PostgreSQL 执行 `INSERT knowledge_base` 或查询 `model_profile`，然后报 relation does not exist。

根因是 Spring 容器里同时存在多个 DataSource 和 JdbcTemplate，而业务仓储没有足够明确的限定。修复包括：创建带 `@Primary` 和 `@FlywayDataSource` 的 MySQL DataSource；显式创建 primary JdbcTemplate 和 primary NamedParameterJdbcTemplate；在 ModelProfileRepository、AgentRepository、ConversationRepository、KnowledgeMetadataRepository 构造参数上使用 `primaryNamedParameterJdbcTemplate`；向量仓储继续限定 `vectorJdbcTemplate`。

修复后真实启动日志显示 Flyway 连接 MySQL 8.4，VectorPool 单独连接 PostgreSQL，知识库创建与模型查询恢复正常。

## 故障六：验收进程没有模型密钥

独立 8081 验收后端没有继承用户启动 8080 时设置的 `DEEPSEEK_API_KEY`。因此 RAG 请求返回 `run → sources → error`。这不是检索失败：sources 已经证明文档命中，error 明确指出密钥环境变量未设置。用户在设置密钥的 PowerShell 中重启新后端后，完整回答成功。

## 排障方法总结

先把链路拆成容器健康、数据库迁移、业务 CRUD、向量写入、检索、模型调用和前端渲染，再分别验证。不要把一个最终“回答失败”直接归因于模型或 RAG；SSE 事件顺序、服务日志和数据库连接池名称能快速确定失败发生在哪一段。

## 故障七：查询指令让语义排序退化

在知识包扩充前的冻结语料上，Qwen 候选无查询前缀时 Recall@5 为 100%、MRR 为 0.8160。生产实现最初按照 instruction-aware 模型的常见建议，为每个问题添加统一中文任务说明。复测后 Recall 没变，但 MRR 降到 0.6917，相关文档更常排在后面。

这不是接口或维度错误，而是提示前缀改变了向量空间中的查询表达。修复是保留 queryInstruction 配置能力但默认置空，并重新运行同一冻结题集，MRR 恢复到 0.8160。知识包扩充后又在新语料上复测，仍采用无前缀方案。经验是 embedding 的 prompt 必须在本领域语料上做消融，而且语料变更后新旧方案要一起重跑。

## 故障八：Ollama 模型目录漂移导致文档索引失败

后端、MySQL 和 pgvector 都正常启动，但上传文档返回“文档解析失败：未知解析错误”。分层检查发现文件解析并不是根因：Ollama 进程未运行，桌面程序启动又报 `Unable to init instance: Unspecified error`。进一步用服务模式启动时看到 `OLLAMA_MODELS` 被当前进程环境改成空的 `D:\ollama-models`，而已经下载的模型实际位于 `C:\Users\zgy19\.ollama\models`。

用正确模型目录启动 `ollama serve` 后，`/api/tags` 能看到 `qwen3-embedding:0.6b`，`/api/embed` 返回 1024 维向量，文档可重新索引。代码同时把连接异常包装成包含 Ollama 地址、模型名和处理建议的错误，并在服务端记录完整异常栈。经验是 embedding 服务属于 RAG 上传链路的运行时依赖；排障既要检查端口，也要核对进程实际继承的模型目录，不能只确认模型曾经下载过。

## 故障九：可选知识库空字符串触发外键约束

工具阶段上线后，用户创建名称全新的“查时间”Agent，选择“不使用知识库”并绑定 current_time，却收到“名称已存在或引用的数据无效”。第一次排查看到数据库已有其他 Agent，错误地把问题归因于同名创建；用户截图明确显示新名称并不重复，促使排查回到实际请求字段。

MCP 阶段第一次运行全量测试时，生产代码已经编译，但新增协议测试在构造嵌套 `Map.of` 响应时少了一个右括号，导致 testCompile 失败。处理方式不是跳过测试，而是把深层一行表达式拆成 `schema`、`tool` 和 response 三个局部变量，修复可读性后重跑全量测试。H2 随后成功应用 V1 至 V6，23 个测试全部通过。这个问题说明协议 fixture 也属于需要维护的测试代码，过度压缩会降低错误定位效率。

真正根因是前端用空字符串 `""` 表示“不使用知识库”。后端校验时跳过了空字符串，却又原样写入 `draft_knowledge_base_id`；MySQL 将它当成一个实际 ID，因找不到对应 knowledge_base 而触发外键约束。修复采用双重保护：前端提交前把空值转换为 null，后端再把 null、空字符串和纯空格统一归一化为 null。测试直接以空字符串创建无知识库 Agent，并断言持久化模型值为 null。

排查过程中也补齐了独立的体验缺口：Agent 卡片现在可以编辑草稿，并提供精确重名提示。但这不是“查时间”创建失败的根因。经验是通用数据库异常会掩盖具体约束，诊断必须核对用户实际输入和请求中的 null/空字符串语义，不能仅凭错误文案推断。

## 新增第二种 MCP 传输后测试替身选择失败

加入 stdio 后，Spring 容器同时存在 StreamableHttpMcpClient 和 StdioMcpClient。原集成测试按接口类型声明一个 `@MockitoBean McpTransportClient`，启动时立即报“找到两个候选 Bean，无法决定替换谁”。这不是业务运行失败，也不是 stdio 协议错误，而是测试夹具仍假设接口只有一个实现。

修复时没有把某个实现重新标成全局 Primary，因为生产本来就需要两个实现并由 transport 路由。测试改为精确替换 StreamableHttpMcpClient，并明确 stub 它的 transport；服务在生产中按配置选择实现。这个问题说明扩展策略模式时，测试中的“按抽象类型替身”也属于需要同步审查的隐含单例假设。
