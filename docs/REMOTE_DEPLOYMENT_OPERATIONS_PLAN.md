# 个人网站受控远程部署与运维计划

## 1. 适用对象与事实基线

本计划针对本地快照 `D:\idea_work\shiguangxv` 及其对应的 `old-things` 生产部署。这里只把快照中的配置与交接记录作为事实来源，不执行其中的部署命令，也不读取或展示服务器 `.env`、数据库密码、管理员密码或 SSH 私钥。

当前可确认的部署结构：

- 生产目录固定为 `/root/opt/old-things`，Compose 项目名固定为 `old-things`；
- 当前服务器快照中的 Compose 文件为 `compose.yml`，服务固定为 `nginx`、`app`、`mysql`、`phpmyadmin`；
- Nginx 对外监听 80，反向代理 Spring Boot `app:3000`，并直接提供 uploads；
- 应用镜像由 Dockerfile 复制根目录预构建的 `app.jar`，Compose 构建本身不会从 Java 源码编译 JAR；
- MySQL 使用必须保留的命名卷 `old-things_mysql-data-reuse`，uploads 使用生产目录下的持久化目录；
- 应用和 MySQL 已有容器健康检查，Nginx 和 phpMyAdmin 没有独立健康检查；
- 应用当前使用 Hibernate `ddl-auto: update`，代码回滚不等于数据库结构可以安全回滚；
- 生产备份根目录为 `/root/opt/old-things-backups`，不得删除既有备份；
- 现有 Agent Studio SSH 工作区根为 `/root/zzh`，不包含生产目录。不得为了部署把通用 remoteRoot 放宽为 `/root`。

## 2. 总体判断

下一阶段不能开放任意 Docker、Nginx、Shell、日志、数据库或文件操作。应增加独立的“部署目标配置”，复用现有 SSH 主机、端口、用户名、密码凭据和固定 SHA-256 主机指纹，但把生产目录、Compose 项目名、健康地址和备份目录固化为平台配置。模型只能选择平台提供的固定任务。

`walicode` 与 `walissh` 的价值主要在工作台体验，而不是它们较宽的命令权限。Agent Studio 后续应形成类似的三栏远程工作台：左侧连接与文件树，中间文件、差异、任务输出和部署状态标签页，右侧 Agent 对话、运行步骤与审批。这里的“终端”必须是不可编辑命令的受控任务控制台，不是真实 PTY，也不接受粘贴或模型生成的 Shell 文本。

开发顺序必须是：

1. 审批目标绑定加固；
2. 建立类似 WaLiCode/WaLiSSH 的远程工作台骨架；
3. 固定生产目标和只读部署诊断；
4. 可验证、不可覆盖的发布前备份；
5. 本地构建与不可变制品暂存；
6. 受控发布、健康验证和失败自动回滚；
7. 最后才评估有限日志诊断和日常运维。

第一阶段不执行部署，也不修改生产容器或数据。

## 2.1 产品形态：受控远程工作台

界面以 `walicode` 为主要工作台参考，以 `walissh` 为 SSH 状态与远程操作反馈参考，但继续使用 Agent Studio 现有安全主链。

首版布局：

- 左侧：SSH/部署目标、连接状态、受保护的远程文件树和固定任务入口；
- 中间：可切换的“概览、文件、变更、任务、部署、输出”标签页，支持多标签但不开放任意终端；
- 右侧：Agent 对话、RunStep 时间线、一次性审批卡和结果制品；
- 底部：当前目标、连接状态、运行状态、耗时和输出截断提示。

对应关系：

| 参考项目能力 | Agent Studio 中的安全实现 |
| --- | --- |
| SSH 服务器列表 | 固定指纹的工作区/部署 Profile，不允许 Agent 改连接目标 |
| SFTP 文件树与编辑器 | 人工直接只读浏览授权根；写入仍使用摘要绑定的精确文本补丁与审批 |
| 终端标签页 | 受控任务控制台，显示固定任务的规范命令与流式输出，命令不可编辑 |
| 命令面板 | 平台定义的任务目录，只能选择枚举任务与受限相对路径 |
| Diff/Artifact 卡片 | 补丁差异、摘要、目标和批准/拒绝状态，继续进入 RunStep/AuditEvent |
| 右侧 AI 助手 | AgentVersion 绑定的对话、工具步骤、审批和执行证据 |
| SSH 运维面板 | Compose 服务、健康状态、发布指纹、备份和发布历史卡片 |

明确不复制：任意 Shell/PTY、任意命令面板、`sudo`、`rm`、`apt`、任意 `docker exec`、任意 Git 写操作、模型自定义参数/环境变量以及脱离 AgentRun 的后台任务。

现有 Agent Builder、知识库、MCP、运行历史和安全审计页面继续保留。远程工作台应作为新的一级页面逐步接入，而不是一次性重写当前管理界面。

## 2.2 首个可见版本

为了尽早得到接近两个参考项目的使用感，首个可见版本不等待完整部署链，先交付：

1. 三栏远程工作台和标签页框架；
2. 复用现有 SSH 配置提供不调用模型的授权根文件树；
3. 人工直接只读文本预览，以及已有远程文本补丁的差异/审批入口；
4. 五种现有 SSH Exec 任务的可视任务卡和输出控制台；
5. RunStep、ApprovalRequest、AuditEvent 在同一工作台内联展示；
6. 为后续部署 Profile、备份、发布和回滚预留“部署”标签页。

任务控制台首版可以在任务完成后展示完整有界输出；后续再增加服务端受控输出事件，实现实时追加。不得为了模拟终端而引入交互式 Shell。

## 3. 阶段 A：审批目标绑定加固

现有 HIGH 审批会保存 `targetEnvironment`，但批准后执行前只校验参数摘要，没有再次确认工具当前目标仍与审批时一致。普通工作区里这是配置竞态；进入生产部署后必须先收口。

改造要求：

- SafeExecutionGateway 在创建审批时保存目标快照；
- 批准后、工具执行前重新解析目标；
- 当前目标与审批目标不一致时形成 `TOOL_TARGET_CHANGED` 或等价失败审计，禁止执行；
- 目标摘要至少包含 SSH 主机、端口、用户名、部署根、Compose 项目名和固定健康地址；
- 增加“等待审批期间修改部署配置”的集成测试，确认不会在新目标上执行旧审批。

这项加固应同时保护已有本地 Coding、SSH/SFTP 和后续部署工具，不能只在新工具内部临时处理。

## 4. 阶段 B：固定部署目标与只读诊断

### 4.1 独立部署配置

新增单一部署 Profile，不复用通用 remoteRoot 充当生产根。首版字段固定为：

- SSH 连接：引用现有 SSH 工作区的主机、端口、用户名、密码凭据和主机指纹；
- 本地源码根：`D:\idea_work\shiguangxv`；
- 远程部署根：`/root/opt/old-things`；
- 远程备份根：`/root/opt/old-things-backups`；
- Compose 文件：`compose.yml`；
- Compose 项目名：`old-things`；
- 固定服务集合：`nginx`、`app`、`mysql`、`phpmyadmin`；
- 固定站点健康地址：服务器回环地址上的 HTTP 80 根路径。

保存和连接测试时应通过 SFTP 逐级 `lstat`：拒绝符号链接根目录，确认 Compose、Dockerfile、Nginx 配置和 `app.jar` 都是普通文件，按当前 Compose 确认 `data/uploads` 是目录。只确认 `.env` 存在且是普通文件，不读取内容。

### 4.2 固定诊断工具

新增 `inspect_remote_deployment`，标记为 `SSH/EXECUTE/HIGH`。模型参数只有固定 `task`，没有 path、命令、参数、环境变量、服务名、容器名或 URL。

首版任务：

- `COMPOSE_VALIDATE`：使用固定项目名和固定 Compose 文件做配置校验，不输出展开后的环境配置；
- `COMPOSE_STATUS`：查看四个固定服务及其健康/运行状态；
- `NGINX_VALIDATE`：在固定 Nginx 容器中执行配置语法检查；
- `SITE_HEALTH`：从服务器本机访问固定健康地址，不允许重定向到任意地址；
- `RELEASE_FINGERPRINT`：只返回 `app.jar`、Dockerfile、Compose 和 Nginx 配置的 SHA-256、大小与修改时间，不读取 `.env`。

结果统一返回：task、SSH 目标、部署根、Compose 项目、successful、exitCode、durationMs、output、outputTruncated。非零退出码仍是可审计结果；连接失败、目标变化、标记异常、超时和通道异常才是工具失败。

限制建议：单任务 30 秒、外层 45 秒、输出 16000 字节；stdout/stderr 明确合并，超时和中断关闭 Exec Channel。

### 4.3 自动化范围

使用进程内 Apache MINA SSHD 的 SFTP + Exec Channel 覆盖：

- 固定命令映射和同会话校验；
- 部署根越界、符号链接、缺失/错误标记；
- Compose 项目名和服务集合固定；
- `.env` 不读取、不回显；
- 成功、非零退出、超时、输出截断；
- 目标配置在审批等待期间变化时拒绝执行；
- AgentVersion、ToolRegistry、RunStep、ApprovalRequest 和 AuditEvent 主链。

阶段 B 完成后先在真实服务器做只读验收，不执行 `up`、`restart`、`down`、`build` 或 Nginx reload。

## 5. 阶段 C：发布前备份

新增独立 `prepare_remote_deployment_backup`，标记为 `SSH/WRITE/HIGH`，没有模型自定义路径。每次创建全新的时间戳目录，禁止覆盖和删除旧备份。

备份内容：

- MySQL 一致性逻辑备份，凭据只在容器内部解析，不进入命令输出和审计；
- uploads 压缩包；
- `app.jar`、Dockerfile、Compose、Nginx 配置；
- 服务器端安全复制的 `.env`，权限保持为仅所有者可读，不把内容传回 Agent Studio；
- 当前容器镜像 ID、制品 SHA-256、Compose 项目与服务状态清单。

完成条件不是“命令退出码为 0”而已：数据库导出和 uploads 归档必须非空，manifest 必须完整，所有文件必须计算摘要。任何一步失败都将本次备份标记失败，且后续部署不得启动。

首版不实现自动清理历史备份，避免保留策略错误造成不可恢复删除。

## 6. 阶段 D：构建与不可变制品

当前 Dockerfile 直接复制根目录 `app.jar`，所以发布链必须显式解决“源码、测试结果和 JAR 是否一致”。建议：

1. 在固定本地源码根执行 Maven 全量测试；
2. 通过后执行固定 package，禁止 `skipTests` 和模型自定义 Maven 参数；
3. 对 JAR、Dockerfile、Compose 和 Nginx 配置计算 SHA-256；
4. 以平台生成的 releaseId 上传到新的暂存目录，禁止覆盖生产文件；
5. 服务器再次计算摘要并与本地 manifest 对比；
6. 使用 releaseId 构建不可变应用镜像标签，保留前一镜像 ID。

模型只能选择“构建候选版本”或引用平台已经产生的 releaseId，不能提供本地路径、远程路径、镜像名、Dockerfile、构建参数或 registry。

## 7. 阶段 E：受控发布与自动回滚

发布工具必须是单一事务式流程，而不是向模型暴露一组可自由排列的 Docker 命令：

1. 核对审批目标、releaseId、当前生产指纹和最近成功备份；
2. 校验 Compose 配置与候选镜像；
3. 只更新 `app` 服务，不运行 `docker compose down`，不触碰 MySQL 卷；
4. 等待容器 health；
5. 验证站点首页及至少一个只读业务页面；
6. 如 Nginx 配置有变化，先在容器内 `nginx -t`，通过后才 reload；
7. 任一健康检查失败时恢复前一应用镜像并再次验证；
8. 返回 deployed、rolledBack、releaseId、previousReleaseId、各阶段耗时和有界输出。

禁止项：

- `docker compose down`、`down -v`、volume rm、system prune；
- 任意 `docker exec`、Shell、sudo、服务名或容器名；
- 输出 `.env`、数据库凭据或令牌；
- 自动恢复数据库备份；
- 修改/删除 uploads；
- 未经健康验证即把运行标记为成功；
- 后台脱离 AgentRun 的部署任务。

## 8. 数据库回滚前置条件

当前 `spring.jpa.hibernate.ddl-auto=update` 会让新应用启动时自动修改生产库结构。这样即使容器镜像回滚成功，数据库也可能已经与旧代码不兼容。

在开放正式发布前必须二选一：

1. 推荐：引入 Flyway，把生产配置改为 `ddl-auto=validate`，所有结构变化使用可审阅迁移；
2. 过渡期：部署工具只允许“无实体/表结构变化”的版本，并由人工确认，但这只能作为临时限制。

数据库备份恢复属于独立灾难恢复流程，必须二次明确确认，不能在普通发布失败时自动覆盖生产数据库。

## 9. 站点配置的后续加固建议

这些不是部署工具首版的必做代码，但应进入网站运维清单：

- 给 Nginx 增加容器健康检查；
- 将 phpMyAdmin 只绑定回环地址或通过防火墙/VPN 访问，避免同时暴露独立端口和公网反向代理路径；
- 为应用增加专用内部健康端点，区分进程存活、数据库就绪和外部页面可用；
- 移除 JWT/管理员口令的弱默认值，缺少生产环境变量时启动失败；
- 固定 Nginx、MySQL、phpMyAdmin 镜像版本或 digest，避免浮动标签导致不可重复发布；
- 增加容器日志轮转、资源上限和磁盘空间预检；
- 域名和证书信息明确后再设计 HTTPS，不让模型提供任意域名或证书路径。

## 10. 推荐的实际开发批次

### 批次 1（下一步立即实现）

- HIGH 审批目标二次校验；
- 新增“远程工作台”一级页面与三栏布局；
- 接入已有 SSH 连接状态、远程文件读取/补丁和五种 SSH Exec；
- 将固定任务、审批卡、运行步骤和有界输出放入同一操作上下文；
- 自动化、前端交互测试、ADR、验证记录和人工验收说明。

### 批次 2

- V12 部署 Profile、后端 API 与前端“部署”标签页；
- 五项固定只读部署诊断；
- Compose 服务状态、健康结果和发布指纹卡片；
- 真实服务器只读验收，不执行发布。

### 批次 2.5（批次 3 前的界面收尾，已完成并人工验收）

- 为“操作助手”和对话测试台的 LLM 消息增加安全 Markdown 渲染，至少支持标题、段落、列表、强调、行内代码、代码块、引用、链接和表格；
- 默认禁用原始 HTML，链接使用安全协议与新窗口隔离，避免 Markdown 带来 XSS、脚本 URL 或样式注入；
- 代码块保留换行并允许横向滚动，表格限制在消息卡片内部滚动，不重新引入整页被内容撑高的问题；
- 用户消息和工具原始 JSON/日志保持纯文本或专用结构化展示，避免把不可信工具输出误当作 Markdown；
- 为常见 Markdown、超长代码/表格、恶意 HTML/链接、流式未闭合语法和纯文本回退补前端测试与人工验收。

实现选择为 `react-markdown + remark-gfm`：不启用原始 HTML，只让 Agent 消息进入渲染器；用户消息、审批参数和工具原始输出保持纯文本。外部链接仅允许 HTTP、HTTPS、mailto，并使用新窗口隔离；远程图片不自动加载，避免模型输出触发跟踪请求。代码块和表格只在消息卡片内部滚动。4 项组件测试与前端生产构建通过；用户在真实 `COMPOSE_STATUS` 回复中确认列表、行内代码和表格渲染符合预期。

### 批次 3（自动化已通过、待真实服务器验收）

- 固定备份工具；
- 真实服务器备份验收；
- 备份 manifest 和恢复演练说明，但不自动恢复生产库。

### 批次 4

- 本地 Maven 测试/package；
- 制品摘要、上传与不可变 releaseId；
- 服务器暂存和镜像构建，不切换生产。

### 批次 5

- 单事务受控发布；
- 应用健康检查、Nginx 校验/reload；
- 失败自动回滚到前一镜像；
- 真实发布与故障演练。

### 批次 6

- 有界、脱敏的 app/nginx 日志尾部诊断；
- 磁盘、备份新鲜度和容器健康巡检；
- 在真实需求出现后再评估定时巡检，不默认增加后台守护任务；
- 只有出现明确业务需求后，才单独评估“仅供人工操作、模型不可访问”的录制型终端模式；它不属于当前路线图承诺。

## 11. 本阶段验收口径

批次 1 只能宣称“受控远程工作台已自动化验证/已人工验收”，不能宣称部署诊断、网站部署、回滚或数据库恢复已经完成。批次 2 只能宣称只读部署诊断；只有批次 3–5 分别通过自动化和真实服务器演练后，才可表述为“完成备份—构建—发布—健康检查—失败回滚闭环”。
