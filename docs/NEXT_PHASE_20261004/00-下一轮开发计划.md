# 下一轮开发计划：流程约束下的 AI 开发运维闭环

日期：2026-10-04。性质：产品与技术开发计划，不是功能完成报告，也不是生产执行授权。

配套文件：[简历表述与证据审计](01-简历表述与证据审计.md)。历史业务验收：[开发到上线复盘](../DEV_TO_PROD_RETROSPECTIVE_20261004.md)。

2026-10-05 更新：新需求含数据库变更已成功发布，规划进入具体批次。以 [任务闭环开发规划与分批交接](03-任务闭环开发规划与分批交接-20261005.md) 的最新现状、实施顺序和验收闸门为准；本文件其余现状是 10 月 4 日审计快照，不倒填改写历史。

## 1. 本轮目标与产品定位

Studio 面向一般网站的持续开发与运维，用户通过本地对话表达需求，系统组织代码理解、修改、验证、预览、部署及异常处理。先在一个明确支持的技术栈上实现可信闭环，再增加项目适配，不把“面向一般网站”写成“已经支持任意网站”。

本轮要从“用户顺序点击工具、平台开发者在外部会话排障”，推进到“Studio 内的 Agent 执行任务、在授权范围内调查并处理异常”。用户主要承担需求、体验验收和重大风险决策，而不是记住 ID、复制 SHA、拼参数、读 JSON 或打开终端。

项目的技术价值不是多做几个按钮，也不依赖与商业产品功能不同。重点是能解释和证明：长任务怎样可靠推进，AI 怎样依据证据处理未预设异常，权限怎样在能力增强后仍不可绕过，完成效果怎样被独立验证。

已投递简历原文不修改。后续开发补强其真实技术内涵，但不能把之后实现的功能说成投递前已经完成，不能将 AI 辅助实现描述成全部独立手写。

## 3. 架构责任：流程优先，不是流程替代 AI

| 层 | 决定什么 | 不能决定什么 |
| --- | --- | --- |
| 流程与状态机 | 前置条件、证据依赖、合法状态转换、时效、互斥与未知状态处理 | 不穷举所有报错的修复答案，不强迫用户手动编排 |
| Agent | 理解任务，选择合法动作，调查异常，形成修复方案，执行并验证，决定继续或请求帮助 | 不自行扩权，不将检索内容视为授权，不跳过验证或伪造成功 |
| 能力执行器 | 真实读写、测试、预览、SSH、部署以及有界执行结果 | 不以语言解释冒充执行；不默默扩大项目、命令或环境范围 |
| 安全网关与验证器 | 版本授权、参数/目标/材料校验、审批消费、证据确认 | 不让 LLM 自己批准自己的高风险动作，不把工具返回当业务验收 |
| 用户 | 明确需求、体验和风险接受；范围外决策 | 不再作为内部材料传递器或故障日志搬运者 |

主路径是“需求 → 开发与验证 → 预览验收 → 发布准备 → 生产确认 → 上线与核查”。每个阶段允许 Agent 走调查、修复、再验证分支，但不能跨越硬性前置条件。生产切换顺序与安全条件由流程约束；阶段内选择证据、定位问题与修复策略由 AI 承担。

固定任务入口继续作为可测试的基础能力和人工诊断备用入口。新增任务级 Agent 编排，而不是删掉原子工具、只拼成一个大提示词，也不是用一键顺序执行冒充智能体自主决策。

## 4. 工作包与实施顺序

### P0：收口已有实现，建立可追溯基线

先做，不能边扩展边累积无法解释的工作区。

- 与“UI优化”会话核对结果卡、工作流、项目运行配置和 MySQL 验证的在途范围，逐项登记“有代码/已测试/已部署/已验收”。历史文件中“尚未实现”的阶段快照不能当当前事实。
- 整理现有改动归属和提交边界，经核对后分批提交；不批量暂存他人改动，不重置共享工作区。
- 建立一份能力、边界、证据及时间清单，关联每项已投递简历表述。后续交付只更新这份现状索引，复盘保留历史事实。
- 用户只读验收中文结果卡：历史成功、当前状态、未运行、失败、恢复与结果未知明确区分。

完成标准：每项已交付能力有代码与验证来源；新增内容有独立提交/交付记录；本次已成功发版不被重放。缺口明确，而不是将全部在途代码算作成果。

### P1：持久任务、证据身份与安全网关补强

这是长任务和自主决策的共同底座，不先堆更多工具。

- 以任务聚合承载阶段、尝试、当前目标和唯一下一动作，关联项目/配置修订、AgentVersion、工具契约、源码、候选、镜像、备份与前后生产身份。
- 保留 Run/RunStep/AuditEvent 为原始事实源，区分“调用完成”“工具业务成功”“工作流完成”和“当前生产状态”。补充步骤/事件序号与读取恢复策略；SSE 断线重连只能恢复观察，不能触发操作。
- 认领阶段和幂等键持久化；同目标互斥覆盖工作流和原子入口。双击、多标签、服务重启不得重复派发生产变更。远程副作用不能仅靠本地事务保证 exactly-once：缺回执先核查，禁止盲目重放。
- 重启可恢复任务观察与合法后续操作；不宣称任意执行线程断点续跑。审批失效与执行未知状态单独处理。
- 用维护良好的标准校验器或明确的受支持严格子集补强 Schema：递归对象、数组、enum、长度/范围、组合约束及不支持特性的拒绝策略。业务校验仍校验路径、SQL策略、目标和材料身份；两者不能互相替代。
- 工具契约/执行配置变化必须显式失效或兼容验证，补足“配置版本不可变，但实际执行含义可能随实现变化”的缺口。知识与模型配置引用的快照范围明确记录。

完成标准：正常路径、证据过期、目标/源码变化、非法参数、审批拒绝/过期/重复消费、取消、预算耗尽、重复点击、崩溃及缺回执均有自动化检查；不存在绕过网关的 Agent 写入/执行入口。取消不承诺撤销已发生的副作用。

### P2：证据驱动的 Agent 异常处理闭环

第一轮以构建/测试失败和部署准备异常为切入点，生产变更暂不赋予自由命令权限。

- 提供面向阶段的诊断材料包：实际运行身份、退出码、最近阶段、有界日志、资源/网络观察、已确认副作用、未知范围和证据时间。大日志按片段读取，不因上下文预算丢掉关键失败行。
- Agent 输出可审查的任务计划/决策摘要：依据了哪些证据、有哪些待排除假设、拟执行何种合法动作、预期验证和停止条件。不要求展示模型私有思维链；记录外显决策与执行证据即可。
- 建立“异常 → 收集证据 → 判断 → 修复 → 验证 → 继续/停止”循环，设置总预算、诊断预算、修复次数及无进展判定，避免反复调用同一失败动作。
- 扩展能力采用项目绑定的诊断动作、参数化受控配方及隔离执行，而不是为每个报错写一个分支。若评估后确需更通用的执行能力，先在隔离环境实现资源/网络/文件边界及命令授权，再考虑生产侧，不开放裸 root Shell。
- 网站代码错误允许 Agent 在该项目的授权路径内修改并重测；平台网关、审批、隔离或执行契约错误必须交平台维护，不让业务 Agent 改自己的约束。平台缺能力时创建清晰的阻断说明，不把“已建议修复”算成修复完成。

首批可恢复任务候选：测试失败定位与代码修复、已确认可重试的隔离下载异常、材料过期导致的最小刷新。部署执行结果未知、数据库迁移失败或目标漂移必须先核查，不能归入普通自动重试。

完成标准：真实 LLM 在隔离验收场景中完成至少一个测试修复、一个可恢复环境问题、一个需要安全停止的问题，保存证据与行动轨迹。测试框架只能注入故障和判定结果，不把正确答案、错误类型标签或固定修复步骤提前告知 Agent。失败结果如实进入报告。

### P3：可复用项目适配与真实验证

- 支持矩阵先覆盖 Spring Boot/Maven 网站与 Docker Compose/SSH 发布。相同项目开发新 UI、一般后端逻辑不应重写预览机制；新的运行时、外部依赖或数据语义需要适配与验证，不承诺一次配置适配所有项目。
- 将运行时、构建/测试配方、合成数据、预览健康判定、保护目录、发布目标及恢复边界作为受审项目配置；复用在途实现，不硬编码时光序类名和专用目录作为长期接口。
- MySQL 隔离验证使用临时数据库、合成数据和精确归属的资源，产出真实测试报告；禁止真实生产卷与凭据。H2 UI 预览和 MySQL/Flyway 验证分开显示。
- 接入第二个小型测试项目，证明项目切换、上下文、权限和产物隔离；不以“界面可以新增项目”代替适配验证。
- 产物/缓存清单解释位置、大小、归属、引用、保留原因、可回收状态；验证占用与回收不靠全局 prune。所有生产备份继续保留，删除另行授权。

完成标准：同技术栈的第二项目可用配置接入，不修改核心执行逻辑；数据库变更须经过对应真实隔离验证；不支持的能力明确阻断，不能用 H2 绿灯代替。

### P4：RAG 与 Agent 效果评测、面试证据交付

- RAG 的已测成果仍按冻结语料/题集报告。增加独立开发集校准阈值和拒答，保留测试集用于冻结比较；新增知识内容/模型/切块必须有版本和单因素对照。
- 增加答案引用、关键事实、无证据拒答及端到端采样；将离线检索效果、pgvector 路径表现、生成效果分开，不推导未测结论。检索内容和工具日志属于不可信输入，不可改变授权。
- 冻结任务级评测集，区分正常、可恢复、必须停止、恶意输入和未知故障。框架测试与真实 LLM 运行分别报告，至少增加一种未用于开发修复的异常变体。
- 对同一小型需求记录人类实际工作：需求澄清、审批、点选、参数复制、工具/会话切换、人工排障、活跃时间；不把等待构建时间全部算成人力，也不把安全审批计成零介入。
- 报告任务完成率、自主恢复率、安全停止正确性、未授权副作用、重复执行、重试数、耗时及资源占用；统一分母、样本和环境。没有对照就不报“节省 X%”。
- 形成架构图、两项关键 ADR、一次真实故障复盘、任务证据轨迹及简历逐条讲解材料；可演示事实先于口号。

完成标准：安全约束违反为零；每类场景有完整回执，不删失败样本。小样本只证明这些场景通过，不宣称普遍可靠。用户可独立提出一个小需求，在 Studio 完成开发到验收，除必要风险决策外不用接触命令、摘要和 JSON；如仍需外部开发者修平台，报告中明确计入。

## 5. 审批和自主性的产品决策

目标是减少用户介入，不是去掉安全责任。当前逐项 HIGH 一次性审批保持不变。

以后如引入有限任务授权，必须单独设计并取得确认：绑定项目、路径、目标、动作集合、预算、期限、源码/工具版本和失效条件；授权只覆盖明确范围。范围扩大、生产风险变化及不可逆数据库操作重新确认。生产上线仍有清晰风险确认；本计划不代表批准该授权模式或任何一次上线。

界面向用户呈现任务和风险，Agent 使用中文能力描述；内部仍保留工具名、参数和原始日志供排查。用户看到一个“处理这个需求/准备上线”入口不等于内部只剩一个工具。

## 6. 首个开发增量与不做范围

首个增量：收口 P0，并在现有发布工作流上完成 P1 的状态/身份/结果验证与 Schema 补强；随后以“隔离测试失败 → Agent 定位修改 → 重测”为 P2 的第一个自主恢复案例。先形成可演示闭环，不将 P0–P4 当作一次会话必须全做完的承诺。

暂不做：微服务化、分布式多实例、工作流画布、为技术数量增加中间件、无边界交互式生产终端、任意技术栈兼容、任意数据库自动恢复、自动删除备份。真实生产故障演练另行授权。

每个增量交付：变更清单、提交身份、测试通过/失败/跳过、真实执行与模拟执行的区分、未验证项、用户验收步骤、残留资源及恢复说明。安全检查不通过时修复机制，不通过降低检查力度制造绿灯。

## 7. 与现有文档、并行工作的关系

本计划补充并收敛产品方向，不撤销 [发版体验计划](../RELEASE_EXPERIENCE_PLAN_20261004.md) 中的结果卡、持久材料、互斥与恢复要求。

需要澄清的方向：既有文档所说“平台选定顺序”用于生产安全依赖，不应扩展成“所有调查与修复步骤都预先写死”。流程约束合法性，AI 对异常承担实质判断；纯固定任务执行应明确标记，不能作为自主 Agent 效果。

“UI优化”会话的在途开发继续保留。本计划不修改其文件，也未向它新增执行指令。后续接手者先查看工作区和交付记录，核对阶段再分工，不按本计划盲目重复开发。

## 8. 需要用户补充但不阻断规划的事项

简历投递日期、本人实际承担的架构/代码/验收范围、目标岗位及面试轮次尚未完整提供。代码可证明系统机制，不能独立证明投递时点、本人手写比例或个人已经能讲清每个细节。面试前以实际事实补充；不得用后续新能力倒填历史。
