## 根因与影响判断

服务器错误为 `publish.sh: 1: set: Illegal option -\r`。本地模板前几个字节为 `73-65-74-20-2D-65-75-0D-0A`，即 `set -eu` 加 CRLF，文件共含 162 个 CR 字节。模板加载时直接保留原字节，SFTP 上传后 Linux shell 把 CR 当成选项的一部分，第一行即退出。

这一具体失败没有执行脚本后续的迁移、镜像切换或应用重建，也没有进入脚本内的恢复逻辑。平台在启动脚本前已经新建发布尝试目录并上传脚本，不能说完全没有产物。缺少阶段标记触发了保守回执 `manualInterventionRequired:true`、`databaseMayHaveChanged:true`；这不是数据库变更已经发生的证据，亦不应篡改历史回执以消除警告。

恢复前仍须通过 Studio 只读检查版本历史、线上镜像/指纹和站点健康。如结果与上述身份不同，应先调查其他操作，不直接重试。

## 修复，不缩减能力

1. `PublishReleaseCommands` 在加载受控 shell 模板时统一为 LF，兼容 CRLF、混合换行和开头 UTF-8 BOM，保留 shell 转义及身份占位符。
2. `.gitattributes` 约定 `*.sh text eol=lf`，减少 Windows 检出再次引入同类问题的可能；运行时归一化仍保留，不依赖 Git 设置才能安全执行。
3. 增加换行/BOM 与幂等性测试；模拟 SSH 上传测试断言实际上传文件以 `set -eu\n` 开始且没有 CR/BOM。
4. 实际执行生成脚本的七条临时目录测试仍覆盖成功上线、健康失败恢复、恢复失败、迁移失败、摘要不匹配、过期备份、旧候选缺少入口。仅模拟 Docker/curl 等外部边界，不连接生产。

没有取消数据库兼容检查、健康验证、自动应用恢复、一次性审批、主机指纹或备份有效期，没有通过换 shell 或开放任意命令绕过问题。
