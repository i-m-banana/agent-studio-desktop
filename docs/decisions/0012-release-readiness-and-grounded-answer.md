# ADR 0012：发布就绪诊断与有证据回答

## 状态

已接受，目标版本 `1.0.0-rc1`。

## 背景

主功能闭环完成后仍有两类风险。第一类是“进程启动了，但关键依赖不可用”：数据库、Ollama 模型、模型密钥、数据目录或 MCP 任一项异常，普通健康接口仍可能显示 UP。第二类是“检索到了相关材料，但材料并没有直接回答问题”：向量近邻总能返回最相似片段，不能把相关性等同于事实证据。

## 决策

新增 `/api/system/readiness` 和前端“系统诊断”，逐项检查 MySQL、pgvector、Embedding 实际推理、模型密钥环境变量、数据目录及 MCP 连接。结果分为 READY、DEGRADED、NOT_READY，只展示环境变量名，不读取或返回密钥值。

RAG 增加答案阶段证据契约。知识库完全没有满足检索阈值的片段且 Agent 没有工具时，平台直接返回固定拒答，不调用模型；存在候选片段时，系统提示明确要求先判断证据充分性，对数字、名称、版本、人员、许可和承诺等事实只能依据片段直接回答，并引用来源文件。带工具的 Agent 在知识库无结果时仍可调用工具补充证据。

发布操作通过 PowerShell 脚本固化：预检、一键启动/停止、发布检查、逻辑备份和显式确认恢复。备份覆盖 MySQL、pgvector 与 data 目录；恢复只能读取当前工程 backups 下的目录，并强制要求 `-ConfirmRestore`。

## 后果

系统能区分“HTTP 存活”和“业务就绪”，用户无需从日志猜测环境变量或依赖状态。无召回时的拒答是确定性的，且节省一次模型调用；有候选片段时仍依赖模型遵守证据契约，因此检索层无答案误召回率与最终答案可靠性必须分开评估。当前方案不是 NLI 或独立 reranker，不能宣称彻底消除幻觉。
