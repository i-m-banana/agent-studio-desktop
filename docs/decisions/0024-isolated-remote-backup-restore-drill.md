# ADR 0024：隔离的远程备份恢复材料演练

## 状态

已接受；自动化验证及真实生产服务器隔离材料化演练人工验收通过。

## 背景

创建型备份已经连续两次在真实服务器成功，但“摘要正确的文件存在”不等于“恢复材料能够安全展开”。直接把数据库和 uploads 写回生产目录会扩大权限、破坏线上状态，也会把普通发布失败升级成数据覆盖事故。因此正式发布前先增加一个不接触生产目录的材料化演练。

## 决策

新增 `verify_remote_deployment_backup_restore`，标记为 `SSH/WRITE/HIGH`，Schema 是不接受任何字段的空对象。工具固定选择备份根中名称最新、无 `FAILED` 标记、目录和关键文件均非符号链接的合格备份；模型不能指定 backupId、路径、命令、参数、环境变量或恢复目标。

工具先校验 `SHA256SUMS`、`manifest.sha256`、manifest 中的 backupId/部署根/Compose 项目/固定文件清单和 uploads gzip 完整性，并按归档展开大小、固定文件大小加 256 MiB 安全余量检查可用磁盘，再在固定的 `restore-drills` 子目录中独占创建带随机后缀的新演练目录。它复制数据库和固定部署文件、以 0600 权限复制 `.env`，在隔离目录展开 uploads，拒绝展开后出现符号链接，并逐项比较固定文件。最后生成独立 `drill.properties` 和摘要。

恢复演练不运行 Docker/Compose、MySQL 客户端或 Nginx，不导入数据库，不替换生产文件，不启动或停止容器，不删除备份或旧演练目录。结果固定声明 `productionModified=false` 和 `databaseImported=false`。

## 后果

- 可以验证最新备份可读取、摘要一致、uploads 可展开、数据库及固定部署文件可材料化；
- 不能据此声称数据库 SQL 已成功导入，也不能声称生产恢复或自动回滚已经完成；
- 每次演练会额外占用接近 uploads 展开大小加应用与数据库文件的磁盘空间，首版不自动清理；
- 正式数据库恢复仍需独立的临时数据库演练和更高等级的人工作业流程；
- 后续构建与发布只能把“最近成功备份 + 最近成功隔离演练”作为前置证据，不能绕过统一审批与审计链。
